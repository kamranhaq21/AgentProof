# Adversarial Review — AgentProof v0.1 spine

Method: for each AD, construct two units one level down (two stories, two modules, two independent builders) that each satisfy every Rule and convention as written, then show where they fail to compose. Each pair is closed with a rule concrete enough for import-linter, ruff, a Pydantic validator, or a named test to check. References: `architecture-agentproof.md` (AD-n), `adr-log.md` (ADR-n), `prd-agentproof.md` (FR/AC).

## Verdict

The spine fixes the hard invariants well (status fold, exit codes, canonical form, redaction-at-ingress, frozen models), but it leaves the two seams where independent agents will actually meet — the `Report` construction path and the `run`/`replay` orchestration — without a named owner or a signature, and AD-2's diagram contradicts ADR-002's layer contract on exactly those seams. Two pairs are critical (nobody is allowed to build and write the Report; replay and run can be built as two pipelines that redact differently), six are high (Fixture YAML contract, assertion YAML shape, `run_id` ownership, file I/O in core, `strict=True` validation mode, `skip` ownership). All are closable with roughly ten sentences of additional rule text and one new bottom-layer module.

## Divergence pairs

- **critical** Nobody may build and write the Report (AD-2, AD-11, AD-13, AD-14; gap) — Unit A, the `runner` story, follows the AD-2 diagram literally: the only edges into `runner` are `engine`, `redaction`, `adapters`, `io`, `loading`; `reports` flows only into `cli`. So `runner.run` returns the engine output and leaves Report assembly and `report.json` writing to `cli/commands/run.py` (compliant: "Imports flow only in the direction of the diagram"; `cli` may import anything). Unit B, the `reports.json_report` + `io.artifacts` story, follows ADR-002's layer contract `engine < {reports, compare} < runner < cli` and AD-13 ("binds `runner`" for artifact naming) and FR-22 ("`run` and `trace replay` write a JSON Report"): `runner.run` imports `reports.json_report.build_report(...)`, serializes with `canonical.dumps`, and writes through `io.artifacts` (compliant: layers allow lower imports; `lint-imports` with a layer contract passes, the diagram edge list fails). They break when the two stories land: either `Report` is constructed twice (CLI and runner) with different `run_id`/`started_at` inputs, or `lint-imports` is configured one way and one unit's imports are rejected in CI; meanwhile AD-14 exports `evaluate_suite`, `ScenarioResult`, and `Report` but no suite-level result type, so one agent makes `evaluate_suite` return `Report` (engine then needs run metadata it is not given) and the other makes it return `list[ScenarioResult]` and builds `Report` in `reports`. *Close with:* Replace the AD-2 diagram's "only in the direction of the diagram" with ADR-002's layer contract as the normative text, and name the Report owner: "`engine.evaluate.evaluate_suite(suite: Suite, traces: Mapping[str, Trace | None]) -> SuiteResult` (frozen model in `models.result`, exported in `__all__`; it carries no run metadata). `reports.json_report.build_report(result: SuiteResult, traces: Mapping[str, Trace | None], run: RunMeta) -> Report` is the only constructor of `Report`; `RunMeta` (`run_id`, `started_at`, `ended_at`, `package_version`, `adapter_name`, `adapter_version`) is built by `runner`. `runner` is the only module that calls `build_report` and `io.artifacts.write`; `cli` never imports `reports.json_report`. A test asserts `grep -L build_report` over `cli/`." Add `models.result.SuiteResult` and `RunMeta` to AD-14's `__all__`.

- **critical** Replay and run can be two pipelines that redact differently (AD-10, AD-9, AD-14; gap) — Unit A, the `trace replay` command story, is written in `cli/commands/trace.py` against the public API only: `io` reads bytes → `load_trace` → `redact_trace(trace, rules_from_suite)` → `evaluate_scenario` (compliant: AD-14 says the CLI "calls only these plus `runner` and `io`"; paradigm diagram draws `CLI --> LOAD`). Because "Replay never calls an agent ... needs no credentials" (AC-19.1), the author builds `RedactionRules` from `redact.keys` and `redact.paths` only and does not resolve `redact.env` names from the environment ("no API keys present"). Unit B, the `runner.run` story, resolves `redact.env` to `secret_values`, sets the console scrub, defaults `capture`, then redacts and evaluates (compliant: AD-10 "by the runner"). They break on AC-31.3: a Trace exported from a live run already has the env value scrubbed, but a user-supplied Trace (UJ-2) containing the current `OPENAI_API_KEY` value passes through replay unscrubbed into `replay-<id>.report.json` and the terminal; and AC-19.2/AC-34.2 drift because the two pipelines apply different steps in different orders (capture default, console scrub installation, `fail_on_missing_trace` handling). *Close with:* "There is one orchestration module. `runner.run.run_suite(suite, *, adapter_name, output_dir, clock, env) -> RunOutcome` and `runner.run.replay_scenario(suite, scenario_id, trace_bytes, *, output_dir, env) -> RunOutcome` share one private `_ingest(trace: Trace, rules: RedactionRules) -> Trace` that validates, defaults `capture`, and redacts, and one private `_rules_for(suite, env) -> tuple[RedactionRules, frozenset[str]]` that resolves `redact.env`. `cli/commands/*` import `agentproof.runner` and `agentproof.io` and, for `validate` and `compare` only, `load_suite`/`load_report`/`compare`; an import-linter `forbidden` contract bans `agentproof.redaction`, `agentproof.engine`, and `agentproof.adapters` from `agentproof.cli`." Add a named test: `test_replay_scrubs_env_value_from_foreign_trace`.

- **high** The Fixture Agent has no YAML slot and no base directory (AD-3, AD-9, FR-20, AC-20.2; gap) — Unit A, the `models.suite` story, defines `Scenario` as `frozen=True, extra="forbid"` with fields `id`, `input`, `assertions`, `skip` (compliant: AD-3; the Glossary lists exactly those). Unit B, the `adapters.fixture` + `init` template story, needs per-scenario "referenced Trace JSON files" and a Suite-level switch that "fixes timestamps and derives the run id from the Scenario id", so the template writes `scenarios[].trace: traces/approve.trace.json` and `defaults.fixture: {deterministic: true}` (compliant: nothing in the spine names these keys, and AD-9 says only that the adapter "never reads them from the environment"). They break the moment `init` output is loaded: `extra="forbid"` rejects `trace` and `fixture` with exit 2, and UJ-4 dies. Even with the key agreed, the fixture must resolve `traces/approve.trace.json` against something: `RunContext` carries `run_id`, `started_at`, `output_dir`, `logger` and no Suite directory, so Unit B resolves relative to the current working directory (compliant) while the template assumes the Suite file's directory (compliant), and the GitHub Actions job (`agentproof run examples/expense-agent/suite.yaml` from the repository root, FR-32) fails with `TraceMissingError`, exit 3. *Close with:* "The Suite schema (v1) is: `version: int`, `name: str`, `defaults: Defaults`, `scenarios: list[Scenario]`. `Defaults` = `adapter: str = "fixture"`, `fail_on_missing_trace: bool = True`, `compare: CompareDefaults` (`include_arguments: list[str] = []`), `redact: RedactDefaults` (`keys: list[str]`, `paths: list[str]`, `env: list[str]`), `adapter_config: dict[str, JsonValue] = {}`. `Scenario` = `id`, `input: JsonValue`, `assertions`, `skip: str | None`, `adapter_config: dict[str, JsonValue] = {}`. Adapter-specific settings live only under the two `adapter_config` maps, and each adapter module exports a frozen `Config` model it validates them with at `runner` resolve time (invalid → `SuiteError`, exit 2). The fixture's config is `{trace: str, deterministic: bool = true}`, where `trace` is a relative path resolved against `RunContext.suite_dir`. `RunContext` fields are exactly: `run_id: str`, `started_at: str`, `suite_dir: Path`, `output_dir: Path`, `logger: logging.Logger`, `adapter_config: dict[str, JsonValue]` (defaults merged under scenario)." Commit `tests/fixtures/schema/v1/suite.yaml` as the single source both stories test against.

- **high** Two YAML shapes for one assertion (AD-8; gap) — Unit A, the `assertions.builtin` story, implements AD-8 literally: each config model has `type: Literal["tool_not_called"]` plus its own fields, so YAML is `- {type: tool_not_called, tool: approve_expense}` and `- {type: tool_call_count, tool: x, equals: 2}` (compliant). Unit B, the `init` template and docs story, copies the PRD's own notation — UJ-1 says the scenario "fails on `tool_not_called: approve_expense`" — and writes `- tool_not_called: approve_expense` and `- tool_call_count: {tool: x, less_than: 3}`, relying on `loading.suite` to normalize before the discriminated union (compliant: AD-8 constrains the model, not the YAML; a normalizer in `loading` is core and pure). They break at `agentproof run` on the generated example (exit 2, "field required: type"), and a second time inside Unit A: AC-13.2 "exactly one operator" is expressed by one builder as `equals|greater_than|less_than` sibling keys with a model validator and by another as `operator: equals, value: 2`; `assertion.id` default `<type>-<index>` is assigned by one builder in a `Scenario` model validator (0-based) and by another in `loading.suite` after validation (1-based, "declared index"), so AC-3.1 duplicate-id detection and Report ids disagree. *Close with:* "Assertion YAML is the flat form only: a mapping with `type: <name>`, optional `id: str`, and the type's own keys; no shorthand key form; `loading` performs no normalization. `AssertionConfig` (base) declares `id: str | None = None`; the default id `<type>-<index>` with a 0-based index over the scenario's `assertions` list is assigned by a `model_validator(mode="after")` on `Scenario` using `model_copy`, and uniqueness (AC-3.1) is checked after that assignment in the same validator. Count operators are sibling keys `equals`, `greater_than`, `less_than` of type `int | None` with a validator requiring exactly one. Every built-in config model is documented with one YAML example in `docs/assertions.md`, and `tests/fixtures/schema/v1/suite.yaml` uses every built-in once."

- **high** `run_id` has three owners (AD-9, Conventions "Ids", FR-5, AC-20.2) — Unit A, the `runner.context` story, generates one UUID4 per `run_suite` call, puts it in `RunContext.run_id`, and, because "an adapter cannot bypass validation", rejects a returned Trace whose `run_id != context.run_id` with `AdapterRunError` (compliant: AD-9 says the adapter "never reads them from the environment itself", implying the context value is authoritative). Unit B, the `adapters.fixture` story, implements AC-20.2 and the Conventions row ("derived from the scenario id when the Fixture Agent is configured deterministic"): it sets `Trace.run_id = f"fixture-{scenario.id}"` (compliant: that is the stated convention). They break on every deterministic fixture run (exit 3), or, if Unit A does not check, the Report's "run identifier" is the UUID while each embedded Trace carries a different `run_id`, and `compare` keys on one while golden tests strip the other. The same ambiguity applies to `started_at`/`ended_at`: Unit A stamps them from the runner clock around `adapter.run`, Unit B writes fixed timestamps from the fixture file, and `duration_ms` is computed by one from the runner clock and by the other from the Trace's own timestamps. *Close with:* "`run_id` is per Suite run, generated once by `runner` (UUID4, or `sha256(suite.name + scenario ids)[:32]` when `defaults.adapter_config.deterministic` is true) and placed in `RunContext.run_id`; the adapter copies `context.run_id` and `context.started_at` into the Trace unchanged, and `runner._ingest` raises `AdapterRunError` if they differ. `Trace.ended_at` and `Trace.duration_ms` are set by the adapter from its own clock (the fixture copies them from the file); `Report.duration_ms` is `ended_at - started_at` of the run, computed by `runner`. The engine never sees or sets any of these."

- **high** Core may read files and `open()` for write; nothing stops a second writer (AD-1, AD-11, AD-13, AD-14) — Unit A, the `loading` story, defines `load_suite(path: str | Path) -> Suite` and `load_trace(path) -> Trace`, reading the file inside core (compliant: AD-1 bans only `pathlib` *write* methods and nothing bans `open`, `Path.read_bytes`, or `os.stat`, and the public-API names `load_suite`/`load_trace` with no stated signature invite a path). Unit B, the `runner`/`cli` story, reads bytes through `io` and calls `load_suite(text, source="suite.yaml")` because the paradigm says "no filesystem" in core and the error shape `(<file>:<field>)` needs a source name (compliant). They break at integration (signature mismatch) and again on security: Unit A's loader also happily follows a symlink and never gives `loading.limits` the byte length before parsing, so AC-1.2 "rejected before parsing" is met in one unit and not the other. A sibling pair inside the same gap: the `reports.json_report` story adds `write_report(report, path)` with `open(path, "w", encoding="utf-8", newline="\n")` (compliant: AD-11 "every artifact writer" and "files are always opened with explicit encoding" read as reports-owned writing; `open` is not in the AD-1 ban list; ruff `banned-api` cannot see `Path.write_text` called on an instance) while `io.artifacts.write_atomic` is the temp-then-`os.replace` writer (AD-13) — the report path skips AC-29.3 atomicity and the symlink refusal. Also, no module is named for reading a Report file for `compare` (AC-25.1), so `compare` grows its own `load_report(path)`. *Close with:* "Core functions never receive a path. `loading.suite.load_suite(text: str, *, source: str) -> Suite`, `loading.trace.load_trace(data: bytes, *, source: str) -> Trace`, `loading.report.load_report(data: bytes, *, source: str) -> Report`; `loading.limits.check_size(len(data), source)` runs first in each. `io.artifacts.read_bytes(path)` and `io.artifacts.write_atomic(path, text: str)` are the only functions in the package that call `open`, `os.replace`, or `Path.read_*`/`write_*`. Enforced by ruff TID251 banning `builtins.open`, `io.open`, `os`, `pathlib`, `shutil`, `tempfile`, `time`, `random`, `socket`, `subprocess`, `datetime.datetime.now`, `datetime.datetime.utcnow` with `per-file-ignores` lifting them only for `agentproof/io/**`, `agentproof/runner/**`, and `agentproof/adapters/**`, plus an import-linter `forbidden` contract from the seven core packages to `os`, `pathlib`, `tempfile`, `shutil`, `time`, `random`, `socket`, `subprocess`, and a unit test that greps core source for `open(`."

- **high** `strict=True` validates differently in JSON mode and Python mode, and `datetime` fields break byte identity (AD-3, AD-5, AC-5.3, AC-6.2) — Unit A, the `loading.trace` story, does `obj = json.loads(data)` (to raise a `TraceFormatError` with position info) then `Trace.model_validate(obj)` (compliant). Unit B, the `adapters.fixture` story, does `Trace.model_validate_json(path.read_bytes())` (compliant: adapters import `models` only). Both builders type timestamps as `datetime` because AC-5.3 says "RFC 3339 ... a naive timestamp is rejected" and `datetime` with a tz check is the obvious Pydantic way. They break because under `strict=True` Pydantic accepts an RFC 3339 string for a `datetime` field in JSON mode but rejects it in Python mode, so the same `trace.json` loads through the fixture and fails `agentproof trace validate` with "Input should be a valid datetime"; the same applies to the Suite, where PyYAML already turns an unquoted `2026-10-22T13:05:00+00:00` into a `datetime` object and a quoted one into `str`. Independently, a Trace with `"2026-10-22T13:05:00Z"` re-exported through `datetime` becomes `+00:00`, so export is not byte-identical to import and golden comparisons of foreign traces flap. *Close with:* "All timestamp fields in serialized models are `str` constrained by `Annotated[str, AfterValidator(rfc3339_with_offset)]` (`models.common.Rfc3339`); no serialized model has a `datetime`, `date`, `Decimal`, `UUID`, or `Enum` field. Every serialized model is validated with `model_validate_json(data: bytes)` only; `model_validate(dict)` on a serialized model outside tests is banned by a ruff TID251 entry for `pydantic.BaseModel.model_validate` in core. YAML → Suite goes through `yaml_safe.load_mapping(text)` → `json.dumps` → `Suite.model_validate_json`, with a YAML resolver that leaves timestamps and the YAML 1.1 booleans (`yes`, `no`, `on`, `off`) as strings." Add a schema fixture pair (`trace.json` loaded by both paths) to `tests/fixtures/schema/v1/`.

- **high** `skip` and `fail_on_missing_trace` have no owner, and `evaluate_scenario` has no signature for an absent Trace (AD-6, AD-14, AC-18.2, AC-18.4, AC-34.2) — Unit A, the `runner` story, handles `skip` as orchestration: it does not call the adapter for a skipped scenario, fabricates `AssertionResult(status="skipped", message=reason)` per assertion, and passes `trace=None` to the engine only for genuinely absent traces (compliant: shell owns flow; the engine stays a function of a Trace). Unit B, the `engine` story, puts the rule in the core because AC-18.4 is "Evaluation" and AC-34.2 requires the public API to give the same result as the CLI: `evaluate_scenario(scenario, trace: Trace | None, *, fail_on_missing_trace: bool)` checks `scenario.skip` first, then absence (compliant). They break two ways: with Unit A's runner and Unit B's engine, a user calling `evaluate_scenario(skipped_scenario, trace)` from the public API gets real assertion results while the CLI reports `skipped`, violating AC-34.2; with Unit B's engine and a runner that still calls the adapter for skipped scenarios, a live Run spends model credits on a scenario marked `skip`, and if the adapter returns nothing the engine sees `trace=None`, checks `fail_on_missing_trace` before `skip`, and reports `error` (exit 3) instead of `skipped`. A third variant: whether `fail_on_missing_trace` is passed as a keyword, read from `suite.defaults` inside the engine, or resolved by the runner into a `TraceMissingError` before the engine is called decides whether the scenario appears in the Report at all. *Close with:* "`engine.evaluate.evaluate_scenario(scenario: Scenario, trace: Trace | None, *, fail_on_missing_trace: bool) -> ScenarioResult` is the only place `skip` and absence are interpreted, in that order: `skip` set → every assertion `skipped` with the reason, `evaluated=0`; `trace is None` → one `ScenarioResult` with `status="error"` (or `skipped` when the flag is false), `assertions=[]`, `message="trace missing"`; otherwise all assertions in declared order. `ScenarioResult` carries `evaluated: int` (count of results not `skipped`) and `execution_failure: str | None`. The runner never calls the adapter when `scenario.skip` is set and never fabricates results. `RunOutcome.execution_failed` is `any(r.execution_failure for r in results) or adapter_load_failed or artifact_write_failed`; `RunOutcome.evaluated_assertions = sum(r.evaluated)`; `cli.exit_codes.from_run` reads only those two fields plus `suite_status`."

- **medium** `io.console` cannot reuse the redaction scrub, so there are two scrubbers by construction (AD-2, AD-10, AC-28.2) — Unit A, the `redaction.apply` story, scrubs `secret_values` in every string leaf of `arguments`, `result`, `metadata`, `output`, longest value first, ignoring values under 8 characters (compliant: AD-10 and its `[ASSUMPTION]`). Unit B, the `io.console` story, is forbidden by AD-2 from importing `redaction` ("`io` imports `errors` only"), so it writes its own `logging.Filter` doing `line.replace(v, "[REDACTED]")` for each value in insertion order with no minimum length (compliant: AD-2; AD-10 only says "the same `secret_values`"). They break on AC-28.2's planted value: a 6-character token is scrubbed from the terminal but not from artifacts (or vice versa), a secret that is a prefix of another is half-scrubbed in one place, and `rich` markup characters inside a secret make `replace` miss in the console path. A second break: the filter is "installed by `io.console`" at CLI start, before the Suite (and hence `redact.env`) is loaded, so a `SuiteError` message printed during load that quotes an env value is not scrubbed in one unit and is in the other that re-installs after load. *Close with:* "Add a bottom-layer module `agentproof.constants` (below `errors`, importable by every package) exporting `REDACTED = "[REDACTED]"`, `MIN_SECRET_LEN = 8`, `scrub_text(text: str, secret_values: Sequence[str]) -> str` (pure; sorts by length descending; skips values shorter than `MIN_SECRET_LEN`), `SCENARIO_ID_RE`, `WINDOWS_DEVICE_NAMES`, and `VOLATILE_FIELDS`. `redaction.apply` and `io.console.RedactionFilter` both call `scrub_text`; a test asserts neither module contains the literal `[REDACTED]`. `io.console.install(secret_values: Sequence[str])` is called by `runner` immediately after `_rules_for` and before the adapter is resolved; all output before that point is produced only from Suite text, never from a Trace or the environment."

- **medium** `compare` cannot reuse `cli.exit_codes` (AD-1, AD-2, AD-6) — Unit A, the `compare` story, is core and must not import any `agentproof.cli` name (AD-1) and nothing may import `cli` (AD-2), so it returns `Comparison(regressed: bool, ...)` and `cli/commands/compare.py` does `raise typer.Exit(1 if cmp.regressed else 0)` inline (compliant: AD-2 forces it). Unit B, the `cli.exit_codes` story, implements AD-6 literally: `from_run(run)` "is the only function that produces an exit code", takes a `RunOutcome`, and the compare command therefore fabricates `RunOutcome(execution_failed=False, evaluated_assertions=1, suite_status="failed" if regressed else "passed")` to feed it (compliant: "only function"). They break on AC-25.1/AC-26.4 semantics: in one unit an invalid Baseline (exit 2) reaches `from_run` as an `InputError`, in the other it is handled before; and the "only function" rule is unenforceable because nothing in ruff or import-linter detects a second `sys.exit`/`typer.Exit` site. *Close with:* "`cli.exit_codes` exposes exactly two functions: `from_run(outcome: RunOutcome) -> int` and `from_comparison(cmp: Comparison) -> int` (`1 if cmp.regressed else 0`). `typer.Exit`, `sys.exit`, and `raise SystemExit` appear only in `cli/app.py`, which maps the return value of each command function through these two functions and the `AgentProofError` handlers; enforced by a ruff TID251 ban on `sys.exit`, `typer.Exit`, and `SystemExit` with a `per-file-ignores` exception for `cli/app.py`. Delete the clause '`compare` reuses the same module' from AD-6."

- **medium** `capture.tool_calls` defaulting has two owners and changes assertion messages (AD-9, AC-5.6, AC-12.4, AC-19.2) — Unit A, the `models.trace` story, defines `capture: Capture | None = None` (absent is representable; the Glossary calls the declaration optional) and the runner "sets `capture.tool_calls` to `unknown` when absent" via `model_copy` (compliant: AD-9 says the runner does it). Unit B, the `assertions.builtin.tool_not_called` story, reads `trace.capture.tool_calls` and, per AC-12.4, writes "capture: unknown" into the message when it is `None` (compliant: "an Adapter that omits it is treated as `unknown`"). They break on AC-19.2 and AC-34.2: a user calling `load_trace` + `evaluate_scenario` from the public API never passes through the runner, so the Trace still has `capture=None`; if Unit B's wording differs between the `None` and `"unknown"` branches (or Unit B raises `AttributeError` on `None`, which AD-7 turns into an `error` result), the same bytes give a different `AssertionResult` through the API and through `trace replay`. The exported `scenario-<id>.trace.json` also differs from the adapter's Trace (`capture` materialized), so `trace validate` of an adapter's raw output and of the exported file have different shapes. *Close with:* "`Capture` is a frozen model with `tool_calls: Literal["complete", "partial", "unknown"] = "unknown"`, and `Trace.capture: Capture = Capture()`; absence is not representable after validation, the runner does not touch it, and the clause 'sets `capture.tool_calls` to `unknown` when absent' is removed from AD-9. Assertion messages use the single helper `assertions.base.capture_note(trace) -> str` for the AC-12.4 sentence."

- **medium** The Trace `redaction` block is unshaped and replay re-redacts a redacted Trace (AD-10, AC-31.2, AC-19.2) — Unit A, the `models.trace` story, defines `redaction: RedactionState` with `applied: bool`, `paths: list[str]` as absolute dotted paths into the Trace (`events.3.arguments.api_key`), `env_names: list[str]` (compliant: AD-10 names the three keys and nothing more). Unit B, the `redaction.apply` story, writes `paths` as the configured rule paths that matched (`arguments.api_key`, deduplicated) and, because `redact` "is applied exactly once ... after a Trace is produced or loaded", overwrites the block on every ingress (compliant: it records what it did). They break on replay: a Trace exported after a live run (with `env_names=["OPENAI_API_KEY"]`) is reloaded under a Suite whose `redact.env` is empty, so Unit B overwrites `env_names` with `[]` and the Report now denies that a secret was ever scrubbed; and `paths` from the two units are different strings, so the golden test for the example run fails whichever unit lands second. A `TraceEvent.redacted: true` written by the first pass is `False` again if Unit B recomputes it (nothing matched, values are already `[REDACTED]`) or stays `True` if it merges. *Close with:* "`RedactionState` = `applied: bool = False`, `paths: list[str]` (sorted, deduplicated event-relative key paths in `agentproof` dotted syntax, e.g. `arguments.api_key`, `output.token`), `env_names: list[str]` (sorted). `redaction.redact` is idempotent and merging: `applied = True`, `paths = sorted(old | new)`, `env_names = sorted(old | new)`, `event.redacted = old or new`. Property test: `redact(redact(t, r), r) == redact(t, r)` for every fixture; replaying an exported Trace under any rule set must yield byte-identical events."

- **medium** The canonical serializer is unreachable from `assertions`, and `VOLATILE_FIELDS` is a name list applied at unspecified depth (AD-2, AD-11, AC-16.2, AC-26.1) — Unit A, the `final_output_contains` story, must compare structured Final Output "against its Canonical form text" (AC-16.2) but cannot import `reports.canonical` (AD-2 places `reports` above `engine`), so it uses `json.dumps(output, sort_keys=True, ensure_ascii=False)` with default separators (compliant). Unit B, `reports.canonical.dumps`, uses `indent=2` (AD-11). They break for any user who, following the docs, writes `contains: '"amount": 5'` after reading the Report: a nested object renders on one line in the compact form and across lines in the canonical form, so pass/fail depends on which serializer the assertion used.
