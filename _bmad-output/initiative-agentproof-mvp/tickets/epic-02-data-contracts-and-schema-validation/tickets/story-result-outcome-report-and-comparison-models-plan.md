## Intent

**Problem:** The engine (epic 4), the Report builder (epic 6), `compare` (epic 7), the HTML renderer, the GitHub Actions artifact, and the deferred viewer all read or produce the same three things, and none of them has a shape yet: what one Assertion evaluation returns, what a Scenario and a Suite evaluation fold into, what the JSON Report on disk looks like, and what a Comparison carries. Without `models.result` and `models.report`, each consumer would decide these for itself and the PRD's contract rules (AC-17.1, AC-17.4, AC-22.1, AC-22.3, AC-22.4, AC-26.6) would have no single home (story 2.4; epic 2 R3 and R5).

**Approach:** Add `agentproof.models.result` with `AssertionResult`, `Counts`, `ScenarioResult`, and `SuiteOutcome`, and `agentproof.models.report` with `SchemaVersions`, `Report`, and `Comparison` plus the five small change records a Comparison lists, following the spine's Report seed (Schemas seed; AD-6, AD-13) and the conventions stories 2.2 and 2.3 fixed: `MODEL_CONFIG` (frozen, forbid-unknown, no NaN or infinity, no `strict`), tuples for sequences, `Field(description=...)` on every field, an exact-integer `version` in `SUPPORTED_VERSIONS["report"]` exported with a JSON Schema `enum`, `null` equal to absent for every field with a default (AD-19), and every failure a Pydantic `ValidationError` whose location names the field path. The consistency rule the story names is a validator: `ScenarioResult.counts` must equal the tally of its `assertions` and `Report.counts` the tally over every Assertion Result in the Report, each failure located at the `counts` field. `Comparison` carries `regressed: bool` and the saved-data statement from `constants.STATEMENTS`, which it refuses to alter. Nothing here builds a Report or a Comparison (epics 6 and 7); the models validate what those builders produce and what the loader reads back.

**Decisions delegated by the maintainer (2026-10-22, "approve all, you are the owner"):** where the spine seed fixes a name or a shape it is followed; where it is silent the simplest shape is chosen and recorded under "Decisions for review" in the Code Map below.

## Boundaries & Constraints

**Always:** `models/result.py` and `models/report.py` import only the standard library, Pydantic, `agentproof.constants`, and sibling `agentproof.models.*` modules (AD-2); no name AD-1 bans (purity checker and TID251 apply); every model uses `MODEL_CONFIG` from `models.assertions` and no model-level `strict`; validation goes through `model_validate(dict)` in tests exactly as `loading.parse_report` will do; every validation error names the field path through the `ValidationError` location; every field carries `Field(description=...)`; every public name has a docstring; `mypy --strict` with the pydantic plugin passes; no `from __future__ import annotations`.

**Never:** No building of Reports (epic 6) or Comparisons (epic 7), no status fold (`engine.status.combine` is the only fold, AD-6), no file reading, no JSON or YAML text parsing (epic 3), no rendering; no changes to `constants.py`, `errors.py`, `models/common.py`, `models/canonical.py`, `models/suite.py`, `models/assertions.py`, `models/trace.py`, or `models/__init__.py`; no changes to `pyproject.toml`, `uv.lock`, `.importlinter`, the check entry point, or any shell package; no new exception class (only `errors.py` defines them); the orchestrator commits and pushes, the implementer does not.

**Decisions for review (the spine is silent on each; every one is a one-line change before the schema is published, a version bump after):**

1. `AssertionResult.type` is a non-empty `str`, not the six-value literal from `models.assertions`: a Report records what ran, and tying it to the static union would force a Report schema bump for any later assertion type.
2. `AssertionResult.detail` defaults to `None` (AD-19: optional fields default to `None`); the seed's `{}` is a value the engine chose and still validates. `evidence` is required (FR-17 names Evidence as part of every result) and may be empty.
3. `Counts` has four required fields, one per `Status`, each a strict non-negative int; a Counts never has a missing key. `count_statuses` is public so `engine` tallies with the same function the validators check against.
4. `ScenarioResult.assertions`, `SuiteOutcome.scenarios`, and `Report.scenarios` must have at least one item, mirroring `Suite` (AD-6: a Scenario has at least one Assertion; a Suite at least one Scenario; `replay` produces one Scenario). The check is `require_non_empty` in the after model validator, not `Field(min_length=1)`: pydantic-core's tuple validator counts only the items that validated, so `min_length` adds a misleading "at least 1 item" line beside every element error (the artifact story 2.2 worked around with wrap validators). The error is Pydantic's own `too_short` at the field and the JSON Schema still carries `minItems: 1` through `json_schema_extra`.
5. `ScenarioResult.counts` and `Report.counts` are required and checked, not derived: the builder supplies them and the model refuses an inconsistent artifact (AC-22.3). `execution_failed` on `SuiteOutcome` and `Report` is checked the same way against `any(s.execution_error is not None)` (review pass 1, finding 3). `evaluated_assertions` and `suite_status` are not cross-checked: the fold is `engine.status.combine`'s alone (AD-6).
6. `cost` is `Cost | None` where `Cost` is a strict float ("in the adapter's unit"): the simplest numeric shape that FR-26's "cost differences" can subtract. Strict because lax `float` accepted `"0.25"`, which a JSON contract must not; an integer is still accepted and stored as a float. `CostChange` reuses it. The Trace has no cost field in v0.1, so the engine will leave it `None` until an adapter path exists.
7. `Report.defaults` is required (the Comparison reads `include_arguments` from it, AD-13); `schema_versions` has exactly the two keys the seed shows, `suite` and `trace`, as strict ints `>= 1` and is not checked against `SUPPORTED_VERSIONS` (the embedded Trace's own `version` already is).
8. `suite_id`, `scenario_id`, `run_id` are plain non-empty strings (as `Trace.scenario_id` is); the Suite model owns the id charset.
9. `Comparison` is flat lists of small change records keyed by `scenario_id` rather than one nested per-scenario object, following the spine's wording ("lists per-scenario status changes, assertion-id set differences, ..."); it carries `baseline_suite_status` and `current_suite_status` because FR-26 names Suite Status first, and (review pass 1, finding 2) `failed_assertion_changes` and `event_count_changes` for FR-26's "failed Assertion ids" and "missing or additional Events", beside the status-blind `assertion_id_changes`. It carries no `version` (it is written, never read back; `SUPPORTED_VERSIONS` has no entry and `constants.py` is out of scope) and no `regressed` cross-check against `status_changes` (AC-26.4 is epic 7's rule).
10. `ArgumentChange.path` reuses `CompareArgumentPath` (`<tool>.<argument path>`) from `models.suite`; `baseline` and `current` are `JsonValue` so epic 7 may store one value or the per-call list.
11. `ReportSchemaVersion` uses `Field(strict=True)` for integer-ness (error `int_type`, as `models.assertions.Count` does) rather than a copy of `trace._require_integer`; the `unsupported_version` code the loader keys on is the same as the Trace's. `_null_means_absent` is imported from `models.trace` rather than copied; the refactor sweep (story 2.7) may hoist it.
12. NaN and infinity are rejected by `MODEL_CONFIG`'s `allow_inf_nan=False` (as `Suite.input` does), not by the Trace's walk; for a bare `JsonValue` field Pydantic reports the union branches, with `finite_number` among them, at the field.

## Implementation Notes

**2026-10-23, implementer (worktree `D:\AgentProof-wt-2-4`, branch `story/2-4-result-report-models`, baseline `2a3161f`).**

Decisions taken where the plan left room (the numbered "Decisions for review" in the Code Map hold the ones the spine is silent on; these are the mechanics):

- Probed Pydantic 2.14.1 before designing: (a) a `ValidationError` built with `from_exception_data` and raised from a `model_validator(mode="after")` with `loc=("counts",)` is re-raised with the outer location prepended, so a scenario-level mismatch inside a Report lands at `scenarios.<index>.counts` and a top-level one at `counts`; (b) `MODEL_CONFIG`'s `allow_inf_nan=False` rejects NaN and infinity in a bare `JsonValue` field, at the cost of Pydantic listing every union branch (`finite_number` among them) at the field, and in a `float` field with a single clean `finite_number`; (c) `Field(strict=True, ge=0)` on tuple items reports `int_type` / `greater_than_equal` at `evidence.<index>`; (d) lax `float` accepted `"0.25"` for `cost`, found by the test, fixed with the strict `Cost` alias.
- Non-emptiness of `assertions` and `scenarios` is checked by `require_non_empty` in the after model validators rather than `Field(min_length=1)`. Observed with `min_length=1`: one invalid scenario inside a Report produced `counts_mismatch` at `scenarios.0.counts` plus a spurious `too_short` at `scenarios` ("at least 1 item after validation, not 0"); with the after-validator the same input produces exactly the one error, and an empty list still fails with Pydantic's own `too_short` and message. The schema keeps `minItems: 1` through `json_schema_extra`.
- `count_statuses`, `require_counts`, and `require_non_empty` are public in `models.result` so `models.report` does not import a private sibling name and so `engine` (epic 4) and `reports.build_report` (epic 6) tally with the function the validators check against. `_null_means_absent` is still imported from `models.trace` as a private name; story 2.7 may hoist it beside `MODEL_CONFIG`.
- Error type codes: `counts_mismatch`, `unsupported_version`, `statement_fixed` (custom), `too_short`, `int_type`, `float_type`, `literal_error`, `extra_forbidden`, `frozen_instance`, `finite_number`, `timestamp_type` / `timestamp_format` (Pydantic's own and the Trace's). A Report of version 2 with an unknown key yields both `unsupported_version` and `extra_forbidden`, as the Trace does; the loader rule recorded in the 2.3 plan (prefer `unsupported_version`) applies to `parse_report` too.
- The spine's literal Report seed wrote `counts: {passed: 2, failed: 1}` beside a single `failed` result; the model rejects exactly that (criterion 2's own rule). At the first pass `SEED` in `test_report.py` carried `{passed: 0, failed: 1, error: 0, skipped: 0}`; after review pass 1 (finding 4) the spine seed itself carries the two `passed` results and `SEED` is the spine's form with the `"…"` placeholders for `run_id` and `created_at` filled and `test_trace.SEED` embedded as the Trace. `test_the_spines_former_abbreviated_seed_is_rejected_at_the_scenario_counts` keeps the one-result form's rejection at `scenarios.0.counts`.
- `SuiteDefaults` and its three sub-models (story 2.2) carry no `Field(description=...)`, so `Report.model_json_schema()` has four `$defs` entries without descriptions (`FixtureDefaults.deterministic`, `CompareDefaults.include_arguments`, `RedactDefaults.keys/paths/env`, `SuiteDefaults.*`). The description tests here cover the models these two modules define; story 2.5's "descriptions present for every serialized field" will need the Suite models fixed, which is outside this story's boundary.
