# PRD Quality Review — AgentProof v0.1

Reviewed: `prd-agentproof.md` and `addendum.md` (2026-10-22, revised after the first rubric review and the adversarial review) against `prd-validation-checklist.md`. This is a re-validation. Calibration: public open-source launch, solo maintainer, chain-top (feeds architecture spine and story slicing); developer tool (Python library + CLI); produced headless from `PROJECT_SPEC.md` with the user unavailable, so `[ASSUMPTION]` density is expected and each tag is judged on whether it is a changeable default rather than a missing decision. Findings fixed since the earlier reviews are not repeated; the tail section records each prior critical/high finding's status.

## Overall verdict

The revision holds: every prior critical and high finding from both reviews is addressed in the text, and the fixes were made as product decisions rather than patches (Canonical form, Capture declaration, Baseline-is-a-Report, Exit Code precedence, first-occurrence `tool_order`, duplicate-key and alias rejection, CSP and no-linkify HTML). The thesis in §1 now carries the narrowed wedge from H6, the pivot criterion in §8 pre-commits the one decision a solo maintainer most needs, and the UJ-to-FR cross-references finally match their narratives. What remains is narrow: three medium gaps in Done-ness (which Exit Code an absent Trace earns, Scenario-id file names on case-insensitive filesystems, and the fact that nothing in FR-32 produces the HTML Report UJ-1 opens), plus a dozen low items. This PRD is ready for the architecture spine without a re-draft; the three mediums should be settled in the same pass as OQ-3 and OQ-16.

## Decision-readiness — strong

Decisions are stated as decisions and the trade-offs are mostly named. §1 names the bet ("no server and no account. A Suite file and a Trace file are the whole integration surface") and ties it to OQ-19; §6.2 picks v0.2 for JUnit and says the spec was ambiguous; AC-21.4 states the Adapter default ("v0.1 ships the Fixture Agent and the Adapter protocol") instead of leaving SM-3 to imply an integration exists; NFR-8 records that the addendum's `major.minor` lean "is withdrawn" and why. §8 now has a pivot criterion with a threshold and a gate point ("if fewer than 3 of the interviewed developers would adopt … work pauses at EPIC D and OQ-19 is reopened"), which the first review asked for. The 19 Open Questions remain genuinely open, carry `[B]` marks on five, and each names what it blocks; OQ-4 and OQ-5 now say which addendum leans are proposals versus decisions. The four `[NOTE FOR PM]` callouts sit at real tensions (H6 wedge, FR-19 naming, FR-35 and §6.2 deferrals).

### Findings
- **[low]** The interview gate is stated at two different points (§8 pivot paragraph "Before EPIC E (Trace workflow) starts, the interviews for H1 to H4 must have happened" vs H1 row "Interview 5 to 10 developers before EPIC C ships" and the H6 note "Decide … before EPIC C") — Not contradictory, since interviews before C satisfy before E, but a reader of the table alone sees a different deadline from the reader of the pivot paragraph, and the PO will put the interview story in one epic or the other. *Fix:* pick one gate (EPIC C ship, matching OQ-19 "does not block EPIC A or B") and use it in the pivot paragraph, the H1 row, and the H6 note.
- **[low]** OQ-3 asks the maintainer to confirm the exit-3 rule without naming what it costs (AC-27.3 "A run exits 3 when an Adapter raised for any Scenario … this takes precedence over 1"; OQ-3) — The chosen rule means one flaky Adapter raise on one Scenario turns the whole run into 3 and hides every Assertion failure from the CI Exit Code; the alternative the first review proposed (per-Scenario Adapter exceptions stay Scenario `error`, exit 1) was rejected without the trade-off being written down. *Fix:* add to OQ-3: "Trade-off: a single Adapter raise masks Assertion failures in the Exit Code; the Report still lists them. Alternative: per-Scenario raises stay 1, and 3 is reserved for Adapter load, Suite read, and Report write failures."

## Done-ness clarity — strong

Coverage is now very good for a headless draft: 35 FRs (two deliberate stubs), 112 ACs, nearly all phrased as observable outcomes with Exit Codes, message content, or byte identity, and the vague-adjective count is near zero (NFR-5 lost "or warned about"; NFR-10 lost "without freezing"). The semantic holes the earlier reviews found in the Assertion engine, the Report, the Baseline, Redaction, HTML escaping, YAML loading, output paths, and determinism are each closed with a specific AC and, where it mattered, a test fixture (AC-15.4's `[delete_file, confirm_with_user, delete_file]`, AC-23.2's vector list, AC-28.2 and AC-31.3's planted values). What remains are three places where an engineer would still have to invent a product decision.

### Findings
- **[medium]** An absent Trace has two candidate Exit Codes (AC-18.2, AC-18.5, AC-27.3) — AC-18.2 makes an absent Trace (Adapter "returns none", or Replay file "does not exist") a Scenario `error` under `fail_on_missing_trace: true`, and AC-18.5 says a run where "every Scenario skipped or absent" exits 1. AC-27.3 says a run exits 3 when "a Trace could not be produced or read", which is the natural description of both absent cases, and 3 outranks 1 (AC-27.4). The adversarial review's case (e) is therefore still open: a renamed `traces/` directory in CI exits 1 by AC-18.5 and 3 by AC-27.3. *Fix:* state in AC-18.2 whether an absent Trace is an evaluation-level `error` (exit 1, so `fail_on_missing_trace` toggles between 1 and `skipped`) or an execution failure (exit 3, so the flag toggles between 3 and `skipped`); rewrite AC-18.5 and AC-27.3 to the same answer, and add that case to the AC-27.1 integration matrix.
- **[medium]** Scenario-id-derived file names collide on case-insensitive filesystems and admit Windows reserved device names, while AC-2.5 claims they are "safe as file names on every supported platform" (AC-2.5, AC-3.1, AC-6.4, AC-29.1) — The pattern `[A-Za-z0-9][A-Za-z0-9._-]{0,63}` accepts `Reject` and `reject` as two Scenarios (AC-3.1 rejects only the "same id"), and on Windows and default macOS both write the same Trace file in the Output Directory, so the second silently overwrites the first and Replay (UJ-2) evaluates the wrong evidence. It also accepts `CON`, `NUL`, `AUX`, `PRN`, `COM1`–`COM9`, `LPT1`–`LPT9`, which remain device names on Windows even with a suffix (`NUL.trace.json`). *Fix:* either (a) reject ids that are case-insensitively equal within a Suite in AC-3.1 and reject reserved device names in AC-2.5, or (b) have AC-29.1 write every Scenario artifact under a fixed prefix (`scenario-<id>.trace.json`), which neutralizes device names, and still add the case-insensitive uniqueness rule. Add a fixture for `Reject`/`reject` and `nul` to the NFR-5 malformed-input tests.
- **[medium]** Nothing produces the HTML Report that UJ-1 opens, and `report` has no output location (FR-23, FR-32, UJ-1 "opens the uploaded HTML Report") — FR-22 says `run` writes the JSON Report; FR-23 says `agentproof report REPORT_PATH --format html` renders HTML from it; FR-32's workflow "runs the Suite, uploads the Output Directory" and never runs `report`. A story sliced from FR-32 yields a workflow whose artifact has no HTML, and a story sliced from FR-23 does not know whether the HTML goes to stdout, next to the JSON, or to a flag. *Fix:* add to FR-32: "runs `agentproof report` on the JSON Report so the HTML Report is in the uploaded Output Directory", and add AC-23.6: "`report` writes `<report-name>.html` next to the JSON Report by default; `--output PATH` overrides; the file is written per AC-29.3". Decide whether `run` should render HTML itself (one fewer CI step) and say so in OQ-16.
- **[low]** AC-18.1 read in order makes an all-skipped Scenario `passed` (AC-18.1 "`passed` if all passed or skipped, `skipped` if all skipped") — The third clause already matches the all-skipped case before the fourth is reached. *Fix:* "`passed` if at least one Assertion passed and no Assertion failed or errored; `skipped` if every Assertion skipped".
- **[low]** AC-18.5's exit 1 is not in the FR-27 code table and "required checks" is undefined (FR-27 "0 all required checks passed; 1 one or more Assertions failed or errored"; AC-18.5) — A run with zero evaluated Assertions has neither a failure nor an error, so FR-27's definition of code 1 does not cover it; the rule lives only in AC-18.5. *Fix:* extend code 1 in FR-27 to "…failed or errored, or no Assertion was evaluated (AC-18.5)", and define "required" as "every Assertion not `skipped`".
- **[low]** AC-21.5 asks a conformance suite to verify something it cannot observe (AC-21.5 "An Adapter must surface every tool call it observes or raise … A conformance test suite that any Adapter can run checks this") — A generic test cannot know what the Adapter *observed*; it can only check protocol shape. As written, the AC will be satisfied by a test that proves less than it claims. *Fix:* split: the conformance suite checks that a returned Trace validates, carries a Capture declaration, keeps sequence order, and that Adapter exceptions propagate; "surface every call or raise" stays a documented protocol obligation that each Adapter's own tests cover against a known agent.
- **[low]** AC-28.2's exception-message case silently depends on the planted value also being an environment variable (AC-28.2 "plants a known value under a redacted key, in a named environment variable, and in an Adapter exception message") — Redaction is key-based plus declared-value-based (FR-31). A value that appears only under a redacted key is not scrubbed from a free-text exception message; the test passes only because the same value is declared under `redact.env`. That is correct behavior, but the AC reads as if key-based Redaction reaches exception text. *Fix:* "…plants one value both under a redacted key and in a `redact.env` variable, then places it in an Adapter exception message; asserts it is scrubbed. A value only under a key is not expected in exception text and is documented as outside FR-31 (AC-31.4)".
- **[low]** Replay's JSON Report name versus `run`'s in the same Output Directory (AC-19.4 "Writes a JSON Report into the Output Directory like `run` does"; AC-6.4) — If both use the same documented name, a Replay in a CI checkout overwrites the Report the run produced; if different, `compare` users need to know which to keep. *Fix:* name the Replay Report by Scenario id (`replay-<id>.report.json`) in AC-19.4, or say explicitly that it overwrites.

Adversarial review (`review-adversarial-general.md`), critical/high:

Suite Status is defined, Exit Code precedence is explicit (AC-27.4), evaluation `error` (1) and execution failure (3) are distinguished (AC-21.3, AC-27.2, AC-27.3), and walk-through cases (a)–(d) now have one answer each; case (e), the missing Trace file, still has two (AC-18.5 says 1, AC-27.3 reads as 3), carried as a medium in Done-ness.
