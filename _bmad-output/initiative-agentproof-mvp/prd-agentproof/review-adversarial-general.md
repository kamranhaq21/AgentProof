# Adversarial Review — AgentProof v0.1 PRD

Reviewed: `prd-agentproof.md` and `addendum.md` (2026-10-22), against the risk register in `../2026-10-22-context-assessment.md` §4. Scope: what breaks if an engineer builds exactly what is written, and where a skeptical senior engineer or a competitor attacks.

## Verdict

The PRD is well-structured and unusually honest about its assumptions, but the two things a CI user depends on most, the exit code and the "secrets never leak" promise, are each specified by ACs that contradict one another, so an engineer cannot build either without guessing. Several headline ACs ("byte-identical", "zero network calls", "every string escaped", "no secret in any artifact") are stated as absolutes and then verified by a single example test, which is exactly the gap a security reviewer or competitor will walk through. The determinism and Replay promises are correctly caveated in §4.6 and §5 and then undercut in §1, UJ-2 and UJ-3, which are the parts people actually read.

## Findings

- **[critical]** Exit code for `error` is unresolvable from the Status model (FR-27, AC-27.2, AC-21.3, AC-18.2, Glossary "Exit Code", addendum §C) — FR-27 says code 3 is "execution or integration error"; AC-21.3 says an Adapter exception yields Scenario Status `error`; AC-27.2 and addendum §C say an error-only Suite exits 1 and that "3 is reserved for Adapter and I/O failures". Status is a four-value enum with no cause, so the runner cannot tell an Adapter crash (3) from a missing-evidence `tool_order` (1). Concrete walk-through of what the PRD gives: (a) all passed: exit 0, unambiguous. (b) One Scenario `error` from an Adapter exception, others passed: 1 per AC-27.2, 3 per FR-27 and the addendum; two answers. (c) One `failed` and one Adapter `error`: 1 by "any failure", but FR-27 gives no precedence between 1 and 3. (d) Empty Trace: Assertions error (AC-11.3, AC-12.3), exit 1 or 3, same problem. (e) Missing Trace file with `fail_on_missing_trace: true`: AC-18.2 says Scenario `error`, but no Assertion Results exist, so AC-27.2 ("any `error` Assertion Result") does not even apply, and a missing file is also "invalid input" (2); three candidate codes. Suite Status, which the Glossary says Exit Code is "mapped from", is never defined anywhere. *Fix:* add FR-27 ACs that (1) define Suite Status as a precedence over Scenario Statuses, (2) define Exit Code precedence explicitly (for example `4 > 2 > 3 > 1 > 0`), (3) distinguish `error` caused by evaluation (missing evidence, stays 1) from `error` caused by execution (Adapter exception, missing Trace file, I/O; exit 3) by carrying an `error_kind` on the Scenario result, and (4) make the five cases above the integration-test matrix for AC-27.1.

- **[critical]** The Redaction ACs promise value-based secrecy while the FR delivers key-based redaction at write time, and the two cannot both hold (FR-31 description, AC-31.3, AC-28.2, AC-21.3, AC-17.3, AC-19.2) — FR-31 says Redaction is key-based, applied "before writing", and "never claims it catches secrets embedded in free text". AC-31.3 then requires that a known secret value placed in *Final Output* appears in no artifact; Final Output is free text with no key, so the only way to pass that test is value-based scrubbing the FR disclaims. AC-28.2 requires no secret in terminal output "at any verbosity", but AC-21.3 and AC-17.3 require the Adapter's or Assertion's exception message to be surfaced, and an HTTP client exception routinely contains the request URL or header with the key in it; `--verbose` plus Pydantic validation errors echo offending input values (assessment R2.3). Further, if Redaction runs only "before the artifact is written", a live `run` evaluates the unredacted in-memory Trace while `trace replay` of the saved file evaluates `[REDACTED]`, so a `tool_arguments_match` on any path under a redacted key passes live and fails on Replay, violating AC-19.2 ("same Evaluation Result"). *Fix:* decide the redaction point once: redact the Trace in memory immediately after the Adapter returns, before Evaluation, terminal output, or any write; state that Evaluation always sees the redacted Trace. Rewrite AC-31.3 to cover keyed locations only (arguments, results, metadata under matching keys) and add a separate AC that exception messages and validation errors pass through the same key-based redactor and are truncated. Drop "Final Output" from AC-31.3 or add an explicit `final_output` redaction path. Change AC-28.2 from "no secret value" to "no value of a redacted key".

- **[high]** `skipped` is unreachable, and the one path that could reach it turns CI green with zero checks evaluated (AC-18.1, AC-18.2, FR-27 "all required checks passed") — No FR defines a `skip` field, a condition, or any mechanism that produces a `skipped` Assertion Result, yet AC-18.1 defines precedence for it. The only implied source is `fail_on_missing_trace: false`, whose resulting Status is never stated. If it yields `skipped`, then a Suite where every Trace path is wrong (a renamed `traces/` directory in a PR) produces all-`skipped` Scenarios, which FR-27 maps to 0 because "required" is undefined, and the PR check stays green. *Fix:* either remove `skipped` from v0.1 or define exactly one producer (`fail_on_missing_trace: false` yields Scenario `skipped`) and add an AC: "A Suite with zero `passed` Scenarios and at least one `skipped` exits non-zero" (or exits 0 only with an explicit `--allow-all-skipped`). Define "required check" in FR-27.

- **[high]** The absence proof (`tool_not_called`) is only as good as the Adapter's capture, and nothing in the PRD requires or records capture completeness (§2.1 "Prove a forbidden action did not happen", FR-12, FR-21, FR-5) — If the real-framework Adapter misses a tool invocation (streamed tool calls, nested sub-agent calls, a tool invoked from inside another tool), `tool_not_called: approve_expense` passes and Dana's compliance-flavoured PR check is a false negative. The PRD promises "evidence the agent never called `approve_expense`" with nothing in the Trace that says what the recorder could see. *Fix:* add to FR-5 an optional run-level `capture` field (for example `{"tool_calls": "complete" | "partial" | "unknown"}`) that the Adapter sets; require the Fixture Agent to set `complete`; require `tool_not_called` and `tool_call_count` messages and the Report to say "no `X` among N recorded tool calls" rather than "never called"; add "absence is relative to recorded events" to AC-33.3.

- **[high]** `compare` has no defined input type, and the JSON Report lacks the data it must diff (FR-22, FR-25, FR-26, AC-26.2, Glossary "Baseline"/"Report") — FR-26 diffs "tool-call sequence, tool names and selected arguments, and missing or additional Events". FR-22's JSON Report contains none of these (Status, Assertion Results, Evidence indexes, counts). FR-25's Baseline does. So `agentproof compare BASELINE CURRENT` either requires CURRENT to be a Baseline file (meaning every `run` must also write one, which no FR says) or compares a Baseline against a Report and cannot diff sequences. AC-26.2 "comparing a result against itself" does not say which file. "Selected arguments" has no selector, so two users get different diffs from the same two runs, undermining AC-26.5's "exact comparison". *Fix:* state that `run` and `trace replay` always write a Baseline-format file alongside the Report (or fold the sequence data into the Report schema); state that both `compare` operands are that format; define "selected arguments" as a per-Scenario `baseline.arguments: [paths]` list defaulting to none.

- **[high]** "Byte-identical" is asserted five times with no oracle that survives Windows (AC-6.2, AC-17.2, AC-20.2, AC-22.2, NFR-1, NFR-6) — (1) "Byte-identical except run id and timestamps" is not a test; the test needs a canonicalization step that names every excluded field, and AC-22.2 forgets the "optional timing and cost" FR-22 puts in the Report, so even the exception list is wrong. (2) AC-20.2 fixes timestamps but not the run id FR-5 requires, so Fixture Traces cannot be byte-identical. (3) Python text-mode `open()` writes `\r\n` on Windows and reads Trace files in the locale codepage (cp1252) unless `encoding="utf-8"` is forced; a Trace with a non-ASCII tool argument then evaluates differently on the maintainer's Windows machine and Linux CI, which NFR-6 forbids. (4) Golden files committed from a Windows checkout with `core.autocrlf=true` differ from the Linux CI's bytes, so the golden test itself is platform-dependent. (5) `json.dumps` byte output also depends on `ensure_ascii` and float repr, neither specified. *Fix:* add NFR-1 ACs: all artifacts are UTF-8 without BOM, LF line endings, `ensure_ascii=False`, sorted keys, indent 2, floats by `repr`; readers open with `encoding="utf-8"`; `.gitattributes` marks `*.json`, `*.yaml`, `*.html` as `eol=lf`; the golden test compares after a documented canonicalization that strips a named field list (`run_id`, `started_at`, `ended_at`, `duration_ms`, `cost`). Make the Fixture Agent accept a fixed `run_id` or derive it from a hash of the script.

- **[high]** HTML safety is verified by one `<script>` vector while the claim is "every string escaped" and "never render Trace content as markup" (FR-9, AC-9.1, AC-23.2, §4.5 description) — `html.escape` is correct in element content and double-quoted attributes only. Not covered by the single test: unquoted attributes, the `<title>` element (Scenario id), inline `<style>` if any value reaches CSS, `href`/`src` if any field is linkified (a `tool_result` containing `https://evil.example` will tempt an engineer to make it clickable; assessment R1.6 says never linkify, the PRD does not), and the common pattern of embedding the JSON Report in `<script type="application/json">`, where a result string containing `</script>` breaks out regardless of HTML escaping. There is no CSP requirement, so any slip becomes XSS in the reviewer's browser via the CI artifact. *Fix:* add ACs: a `<meta http-equiv="Content-Security-Policy" content="default-src 'none'; style-src 'unsafe-inline'; img-src data:">` is present; no element carries an `href`, `src`, or event-handler attribute whose value derives from Trace or Suite data; dynamic values are inserted only in element text or quoted attributes; if JSON is embedded, `<`, `>`, `&`, U+2028 and U+2029 are escaped as `<` and so on; the escaping test uses a payload corpus (`<script>`, `"><img src=x onerror=…>`, `</script><script>`, `javascript:`, `&lt;` double-encoding), not one string.

- **[high]** Safe YAML loading as specified still allows two silent-failure classes a PR author can exploit (FR-1, AC-1.1, AC-1.2, AC-2.2, AC-3.1) — (1) PyYAML's `safe_load` accepts duplicate mapping keys and keeps the last. A Suite with two `assertions:` keys under one Scenario silently drops the first list, so a Scenario that visually contains `tool_not_called: approve_expense` ships with only the second block, and AC-2.2/AC-3.1 (which inspect the already-merged dict) cannot see it. Green CI, missing rule. (2) The 5 MB raw-text limit (AC-1.2) does not bound alias expansion; a 1 KB "billion laughs" document with nested anchors expands inside `safe_load` to gigabytes before any model validation runs (assessment R2.1). Multi-document streams (`---`) are unspecified. *Fix:* add ACs: duplicate mapping keys anywhere in a Suite are rejected naming the key and line (a `SafeLoader` subclass overriding `construct_mapping`); aliases/anchors are rejected, or alias expansions are capped (for example 1,000 nodes) and the Suite rejected beyond it; a Suite with more than one YAML document is rejected.

- **[high]** FR-29 as written rejects legitimate CI output paths, and its atomic-write AC does not hold on Windows (FR-29, AC-29.1, AC-29.2) — "Write only inside the resolved target directory" plus "resolves outside the working directory, rejected with exit 2" means `agentproof run --output "$RUNNER_TEMP/reports"` or `--output /tmp/agentproof` (both normal in CI, and `init ../sibling-dir` is a documented form) exit 2. The security goal is "no attacker-controlled path from inside a Suite escapes", not "the user may not choose an absolute path". AC-29.1 covers only `..` and symlinks; on Windows an engineer also has to handle drive-relative `C:reports`, UNC `\\host\share`, reserved device names (`CON`, `NUL` as a filename silently succeeds or hangs), alternate data streams `report.json:hidden`, and `Path.resolve()` on a not-yet-existing path. AC-29.2 "temp file then rename": `os.rename` fails on Windows when the target exists, `os.replace` raises `PermissionError` when the target `report.html` is open in the reviewer's browser or being scanned by antivirus, and the temp file must be on the same volume. *Fix:* split the rule: (a) user-supplied `--output`/`init PATH` may be any path, resolved once, created if missing; (b) every path that originates from a Suite or Trace (fixture trace references, report names derived from Scenario ids) must resolve inside the Suite's directory or the output directory, with a test corpus covering `..`, symlinks, absolute, UNC, drive-relative, device names, and ADS. Rewrite AC-29.2 to "written to a temp file in the destination directory then `os.replace`d; on `PermissionError` the temp file is removed and exit 3 is returned naming the locked path".

- **[medium]** Four built-in Assertions have edge semantics that are undefined or mutually inconsistent (FR-13, FR-14, FR-15, FR-16, AC-12.3, AC-14.2, AC-14.3, AC-15.2, AC-16.2) — (1) `tool_call_count: {tool: approve_expense, equals: 0}` is `tool_not_called` in different clothing, but FR-13 says nothing about an empty Trace while AC-12.3 makes `tool_not_called` an `error` there; two equivalent rules give different Statuses. (2) FR-14: a configured path that does not exist in the arguments (`items.3.amount` on a two-item list) is neither "never called" nor "different arguments"; fail or error is unspecified. AC-14.2 "by type and value": YAML `amount: 1.0` is a float and JSON `1` an int; Python says equal, the AC says not. AC-14.3 is labelled "Errors when…" and then describes the failure message, conflating the two Statuses. (3) AC-15.2 "the first tool found out of order" is undefined under subsequence matching: for `tool_order: [confirm_with_user, delete_file]` and Trace `delete_file, confirm_with_user, delete_file`, a greedy subsequence match passes (indexes 2, 3), which is not what Marcus (UJ-2) wants; and if it fails, which tool is "first out of order"? (4) AC-16.2 "canonical JSON serialization" is undefined; `final_output_contains: '"status": "rejected"'` passes or fails depending on whether the serializer emits a space after the colon. *Fix:* add AC-13.3 mirroring AC-12.3; specify in FR-14 that a missing path is `failed` naming the path, and that numeric comparison follows JSON number equality (1 == 1.0) with the type rule applying only to string-versus-number; specify `tool_order` as greedy leftmost subsequence, document that it does not forbid earlier occurrences, and define the failure message as "expected `B` after `A` (event N); no `B` found after N"; define canonical JSON for AC-16.2 as `json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False)` in the Assertion reference.

- **[medium]** The schema-version policy contradicts itself between PRD and addendum, and FR-20 quietly couples Suite and Trace schemas (AC-2.2, AC-7.1, OQ-5, addendum §C, FR-20) — AC-2.2 rejects unknown fields at any level; addendum §C leans to `major.minor` "with additive-minor tolerance", meaning a 1.0 reader accepts a 1.1 Trace carrying a new field, which AC-2.2 forbids. AC-7.1 "a Schema Version the package does not support" has no definition of "support" under either policy. FR-20 lets the Fixture Agent's scripted Trace live "in the Suite", so the Suite schema embeds the Trace schema and every Trace schema bump is also a Suite schema bump. *Fix:* pick one policy in the PRD (recommended: forbid unknown fields; a reader supports exactly its own major and any minor less than or equal to its own; a newer minor is rejected with a message naming the package upgrade). State in FR-20 that scripted Traces in a Suite are a path reference to a JSON file, never inline YAML.

- **[medium]** "No network, no subprocess" is required to be "verified by test" with no verification mechanism, and AC-4.1 is literally impossible (AC-9.2, AC-19.1, NFR-3, AC-4.1) — A test that patches `socket.socket` to raise catches Python-level sockets in-process and nothing else: not a subprocess, a C extension, or `urllib` from a thread started before the patch. AC-19.1 "with network access disabled" is not something a GitHub Actions step can do on the default runner; it needs a container step with `--network none`, not mentioned. AC-4.1 "without environment variables" cannot be satisfied (Python needs `PATH`, `SYSTEMROOT` on Windows, `HOME`). *Fix:* AC-9.2 and NFR-3: "verified by a pytest fixture that replaces `socket.socket`, `socket.create_connection`, `subprocess.Popen`, `os.system`, `os.exec*`, `os.spawn*`, and `os.fork` with raising stubs for every core-path test". AC-19.1: "verified in CI by running the example Replay inside a container started with `--network none`". AC-4.1: "with no environment variable beyond those the OS and Python require, and with no `*_API_KEY`, `*_TOKEN`, or `AGENTPROOF_*` variable set".

- **[medium]** Two "executed in CI" ACs cannot be executed as written (AC-27.1, AC-33.1, H7, OQ-1) — AC-27.1 requires an integration test that triggers exit code 4 ("internal unexpected error") through the CLI; by definition no documented input does so, and an Adapter exception is already mapped to `error`, so the only way is a hidden injection hook the PRD does not provide. AC-33.1 requires every README command to run in CI; the README's first command is `pip install agentproof`, and today that installs the other author's package (H7), so the doc test would pass against the wrong software. *Fix:* add a documented, test-only `AGENTPROOF_FAULT_INJECT=<site>` variable that the integration test uses and the CLI reference lists as unsupported; make AC-33.1 say "executed against the wheel built in the same CI job, with the install line rewritten to that wheel path"; mark OQ-1 as blocking AC-33.1 as well as FR-33.

- **[medium]** Privacy leaks into the "local-only, no upload" story (FR-5, FR-22, FR-26, FR-32, NFR-4, addendum §B `storage/interface`) — (1) FR-5's "optional environment metadata" has no definition of who populates it; the obvious implementation (`os.environ`, hostname, username) captures exactly the secrets Redaction is meant to remove, and FR-32 then uploads the result to GitHub artifacts. (2) "Cost" in FR-22/FR-26 needs model pricing, which means either a maintained pricing table (stale within weeks, a support burden the non-goals do not want) or a network lookup NFR-3 forbids; neither is chosen. (3) FR-32 uploads Reports containing Trace arguments and results "on success and failure" to a location readable by anyone with repo read access (assessment R1.5), and NFR-4 says "no upload" without reconciling this. (4) The addendum's `storage/interface` module is the first brick of the §6.2 "storage backend abstraction" that is out of scope. *Fix:* define environment metadata as an explicit allow-list set by the Adapter (`python_version`, `package_version`, `platform`) and never from `os.environ`; define cost as an opaque number the Adapter may supply, with AgentProof computing nothing; add AC-32.4 "the workflow and docs state that uploaded artifacts are visible to everyone with read access and that Traces should be redacted or excluded"; remove `storage/interface` from the v0.1 layout.

- **[medium]** The core promise is stated without the qualification the PRD elsewhere insists on, in the three places users actually read (§1, UJ-2, UJ-3, §4.6, AC-26.5, OQ-4) — §1 promises "deterministic pass/fail results" on a live `run`, which is not deterministic. UJ-2 says Replay "reproduces the failure", the exact wording assessment R3.4 flags as misleading. UJ-3 has Priya compare two *live* runs across a model upgrade and read "two Scenarios whose tool-call sequence differs" as a finding, which §4.6 says the tool "never compares as if deterministic"; with sampling temperature above zero those diffs are indistinguishable from noise, and the only remedy (N-run statistics) is deferred to v0.3. The command is still `trace replay` in FR-19, FR-30, UJ-2 and AC-32.3 while the addendum leans to renaming. *Fix:* reword §1 to "deterministic evaluation of recorded behavior"; UJ-2 to "re-evaluates the saved Trace and shows the same failure"; have Priya in UJ-3 run the Suite three times after the upgrade and `compare` report which sequence diffs are stable across all three (or put the sequence diff behind `--show-sequence-diff` with the AC-26.5 disclaimer printed above it); decide OQ-4 in the PRD rather than the addendum.

- **[medium]** NFR-5 and NFR-10 are not acceptance criteria, and one of them forces architecture the non-goals defer (NFR-5, NFR-10, §6.2, AC-23.3) — NFR-5 "rejected or warned about" is two behaviours; a test cannot assert "or". NFR-10 "opens in a browser without freezing" for 10,000 Events in a self-contained, script-free HTML file means a static DOM of roughly 10,000 rows plus arguments; keeping that usable requires either pagination/virtualization in JavaScript (the v0.3 viewer in disguise) or truncation, which collides with AC-23.3. "Without freezing" is unmeasurable. *Fix:* make NFR-5 "rejected" only; replace NFR-10's browser clause with "the HTML Report renders only Events referenced by Evidence plus a bounded context window (default 5 Events either side), with a note that the full Trace is in the JSON Report; the Report for the 10,000-Event Trace is under 2 MB".

- **[medium]** The Vision states as fact what the PRD's own evidence table refutes, and nothing in the PRD stops the build if H1 to H4 fail (§1, §8 H6 and H9, §6.1, OQ-15, OQ-19) — §1: "Teams ship prompt, model, tool, and framework changes with no repeatable way to check that the agent still calls the right tools"; §8 H6 lists four tools that do exactly that today (Promptfoo `trajectory:*`, DeepEval `ToolCorrectnessMetric`, agentevals, EvalView). The PRD says interviews happen "before EPIC C ships", but §6.1 commits the full v0.1 scope regardless of outcome, so the hypotheses are decorative; there is no kill or pivot criterion (assessment R6.5). H9's support is an n=27 survey and one n=306 survey about reliability generally, which the PRD calls weak and then counts as "supported". *Fix:* rewrite §1 to "no framework-neutral, file-based way to check…" (the actual H6 residual); add a §8 gate such as "if fewer than N of the interviewed developers would adopt a Trace file format (H2), v0.1 ships without the real-framework Adapter and launch is reframed as a Trace-format proposal"; downgrade H9 to "Hypothesis, weak indirect signal".

- **[medium]** Four of seven success metrics cannot be measured under NFR-4 (§7 SM-3, SM-4, SM-5, SM-7; NFR-4) — SM-3 "developers who test their own agent within 30 days", SM-4 "users who run a second Suite", and SM-7 "install failures per 100 attempts" all need a denominator (attempts, users) that only telemetry provides; surveys and issues count the self-selected, and SM-7's denominator is unknowable. SM-5 "measured by … clone counts": the GitHub traffic API exposes a rolling 14-day window and counts CI clones, so "100 in the first month" needs weekly polling and still measures bots. *Fix:* restate SM-3/SM-4 as count-based ("at least 5 distinct GitHub accounts open an issue, PR, or discussion showing a non-example Suite"); replace SM-7 with "every reported install or quick-start failure becomes a reproducing test within 7 days"; replace clone counts with PyPI download counts from the public BigQuery dataset.

- **[low]** Glossary terms drift when FRs use them (Glossary "Status", "Exit Code", "Run", "Fixture Agent", "Scenario"; FR-28; AC-22.3; AC-13.1; AC-14.3) — "Exit Code is mapped from Suite Status" but codes 2, 3, 4 are not Statuses and Suite Status is undefined. "Fixture Agent, a built-in deterministic Adapter" stamps wall-clock timestamps unless configured otherwise (AC-20.2), so it is not deterministic by default. "A live Run calls an Adapter; Replay does not" makes Replay a kind of Run while "Replay, Evaluation of a Scenario against a saved Trace" does not; so FR-22's "run identifiers" in a Replay Report are either the Trace's run id or a fresh one, and AC-22.2 ("differ only in run id") implies fresh, which breaks the Report-to-Trace link. "Scenario, an input for the agent, and a list of Assertions" omits `fail_on_missing_trace` and the Fixture Trace reference. FR-28's end-of-run "summary of passed, failed, error, and skipped counts" and AC-22.3's counts are of Assertion Results, so a Suite whose only Scenario has a missing Trace reports "0 failed, 0 error" while exiting non-zero. AC-13.1 ("has a passing and a failing test") is a test-existence statement, not a behaviour. *Fix:* define Suite Status in the Glossary; say Fixture Agent timestamps come only from the script (never the clock) and run id from a hash of the script; state that a Replay Report carries both the Trace's `run_id` and its own `evaluation_id`; make FR-28 and AC-22.3 report counts at both Scenario and Assertion level; replace AC-13.1 with the boundary behaviour (`less_than: 0` rejected at load; `equals` on an empty Trace is `error`).

- **[low]** `init` can leave a half-written scaffold and has a check-then-write race (FR-4, AC-4.2, AC-29.2) — AC-4.2 names "the first conflicting path", implying `init` checks and writes file by file; if the third of four files conflicts, the first two are already on disk and a rerun now conflicts on those. AC-29.2 covers Reports only, not `init` output. *Fix:* "`init` resolves every target path, checks all for existence, and writes nothing if any exists; files are written into a temp directory and moved in one step where the filesystem allows".
